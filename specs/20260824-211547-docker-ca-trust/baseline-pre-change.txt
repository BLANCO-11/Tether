# ─────────────────────────────────────────────────────────────────────────────
#
# T006 says "build all six images from the current HEAD". THAT IS IMPOSSIBLE ON
# THIS WORKSTATION — the pre-change images cannot be built here at all. Measured
# 2026-08-25 against packages/mcp-bridge/Dockerfile at HEAD:
#
#   ERROR: process "/bin/sh -c pnpm install --filter @foundry/mcp-bridge --prod
#          --frozen-lockfile=false" did not complete successfully: exit code: 1
#
# That failure IS the defect this feature fixes, so "capture the before state by
# building the before state" is circular here.
#
# What is recorded instead: the trust state of the three BASE images. This is a
# faithful substitute, and the reason is checkable rather than asserted — at HEAD
# no Dockerfile in this repository adds, removes or modifies any certificate
# authority. Verify with:
#
#   grep -rnE 'ca-certificates|NODE_EXTRA_CA_CERTS|PIP_CERT|keytool|cacerts' \
#     packages/*/Dockerfile infra/*/Dockerfile | grep -vE ':[0-9]+:[[:space:]]*#'
#
# ⚠ The trailing comment filter is NOT cosmetic. Without it the grep hits
# packages/server/Dockerfile:63, a COMMENT explaining why curl and
# ca-certificates were removed from that image — a false positive that makes the
# check look like it found cert logic when none exists. Verified 2026-08-25:
# with the filter, nothing at HEAD.
#
# At HEAD that returns nothing. So each derived image's trusted-authority set is
# exactly its base image's, and the base images are the honest baseline.
#
# ⚠ CONSEQUENCE FOR US2: T026's comparison must therefore be made against the
# BASE image figures below, not against pre-change derived images. A derived
# image built after this feature with CORP_CA_FILE empty must match its base.

# ⚠ T007 — THE FINDING THAT DETERMINED THE DESIGN.
# These four images have NO system trust infrastructure whatsoever: no
# ca-certificates package, no /etc/ssl/certs/ca-certificates.crt, no
# update-ca-certificates, no /usr/local/share/ca-certificates, no openssl.
# Node carries a compiled-in root set and needs none of it.
#
# So the intended "add the certificate to the system store and point every
# toolchain at it" approach is IMPOSSIBLE here, not merely inconvenient. It would
# have worked on two of six images, and the four failures would have read as an
# unrelated problem. This is why the feature uses three mechanisms rather than
# one (research R1, plan.md Complexity Tracking).
#
# It also rules out the obvious repair: installing ca-certificates needs a
# network fetch, which is the thing that is broken.

# ─────────────────────────────────────────────────────────────────────────────
