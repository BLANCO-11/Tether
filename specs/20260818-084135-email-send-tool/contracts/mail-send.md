# Contract: `foundry_email_send` / `POST /api/mail/send`

Two faces of the same thing. The **tool** face is what the drafter sees in the manifest; the
**endpoint** face is what the step executor calls. They must stay in step — the tool's
`paramsSchema` is serialised into the request body verbatim by `invokeTool`.

---

## 1. Tool registration (the manifest face)

Registered by `services/platform-tool-catalogue.ts`.

```ts
{
  name: "foundry_email_send",
  method: "POST",
  url: `${config.mail.selfBase}/api/mail/send`,
  authStyle: "header",
  authParamName: "X-Foundry-Mail-Key",
  secretEnvName: "FOUNDRY_MAIL_KEY",
  description:
    "REAL DELIVERY to a live mailbox — this is not the demo mail service. Sends one plain-text " +
    "email. Leave `to` unset to send to the person who started the run; that is the normal case " +
    "for 'email me the result'. Any address you DO name must be on the workspace's allowed " +
    "recipient list or the call is refused and nothing is sent. Returns " +
    "{status, message_id, recipients[], cc[], attachments[]}. Body is plain text — no HTML. " +
    "Attachments: text files (`.csv`, `.tsv`, `.txt`, `.json`) a step built, or `.csv`/`.xlsx` " +
    "files generated by the server from structured `rows`.",
  paramsSchema: {
    subject: { type: "string",  required: true,  description: "Single line. Newlines are rejected. Max 250 chars." },
    body:    { type: "string",  required: true,  description: "Plain-text message body — put the script output here. Max MAIL_MAX_BODY_BYTES." },
    to:      { type: "array",   required: false, description: "Recipient addresses. OMIT to send to the person who started the run. Every address given must pass the allowlist." },
    cc:      { type: "array",   required: false, description: "Cc addresses. Subject to the same allowlist as `to`." },
    attachments: {
      type: "array", required: false,
      description: "Optional files: either text — [{name, content}], names ending .csv/.tsv/.txt/.json — or generated — [{name, format, rows}] with format `csv` or `xlsx`. At most 5 files, 1.5 MB total.",
    },
  },
}
```

Attachment rules (enforced by `services/mail-attachments.ts`, checked at the route before any
recipient work): the extension allowlist is the control — the content type is derived from the
name and never caller-supplied; files are refused over the cap, never truncated; a generated file
must carry a name whose extension matches its `format`. A real send records `{name, bytes}` only;
the content is held for a draft run's Email box alone.

Note for the drafter (carried in the description, not in a separate prompt edit): omitting `to` is
the *preferred* form. It is the only form that works without an allowlist entry, and it is what
"email me" means.

## 2. Endpoint

### Request

```
POST /api/mail/send
X-Foundry-Mail-Key: <derived key>          # required — mail-key.middleware.ts
x-foundry-run: <flowExecutionId>           # set by invokeTool; absent on a bare tool test call
content-type: application/json

{ "subject": "…", "body": "…", "to": ["…"], "cc": ["…"] }
```

- `workspaceId` in the body is **ignored** (FR-010). Workspace comes from the resolved execution.
- No other fields are accepted; unknown keys are rejected by the zod schema rather than dropped.

### Success — `200`

```json
{
  "status": "sent",
  "message_id": "<graph client-request-id>",
  "recipients": ["asked.person@example.com"],
  "cc": [],
  "resolved_from": "requester"
}
```

`resolved_from` is `"requester"` or `"explicit"` — the run page shows it so the destination is
explainable without reading the flow.

Graph itself answers `202 Accepted` with an empty body; there is no provider-side message id to
return, so `message_id` is the correlation id from the `request-id` / `client-request-id` response
headers. That is stated here because a reader expecting an RFC 5322 Message-ID will otherwise assume
it is one.

### Refusals

| Status | Condition | Body shape |
|---|---|---|
| `400` | Malformed body, unknown field, missing `subject`/`body`. | `{error, detail}` (zod flatten) |
| `401` | Absent or wrong `X-Foundry-Mail-Key`. | `{error: "unauthorized"}` |
| `409` | `MAIL_ENABLED=false`. | `{error, message: "email delivery is switched off for this deployment (MAIL_ENABLED)"}` |
| `422` | No `to` **and** no resolvable person requester. | `{error, message, detail: {runKind, remedy: "name a recipient in `to`"}}` |
| `422` | A recipient failed the allowlist. | `{error, message, detail: {rejected: [...], rule: "…"}}` — **nothing sent** |
| `422` | Over a cap (body bytes, recipient count, subject length/newline). | `{error, message, detail: {actual, allowed}}` |
| `424` | Graph configuration incomplete. | `{error, message, detail: {missing: ["MAIL_GRAPH_CLIENT_SECRET", …]}}` |
| `502` | Token exchange or `sendMail` failed. | `{error, message, detail: {status, graphError, requestId}}` — never the request body |

Every refusal is recorded in `email_sends` with `outcome: "refused"` (or `"failed"` for `502`) and
its reason. The **message body is never in the response, the log, or the row.**

## 3. Recipient resolution (normative)

```
requester := flow_executions[x-foundry-run].requested_by
             where requested_by_kind ∈ {user, replay} and requested_by matches EMAIL_RE
             else null
             # read off the execution row, NOT joined from flow_run_requests — plan.md Decision 3

if to is empty:
    if requester is null → refuse 422 (no requester)
    recipients := [requester]
    resolved_from := "requester"
else:
    for each address in to ∪ cc:
        allowed :=  address == requester
                 OR ( domainOf(address) ∈ MAIL_ALLOWED_RECIPIENT_DOMAINS
                      AND ( workspace allowlist is null
                            OR address ∈ workspace allowlist
                            OR domainOf(address) ∈ workspace allowlist ) )
    if any not allowed → refuse 422 (whole call, no partial send)
    resolved_from := "explicit"

dedupe case-insensitively; cap at MAIL_MAX_RECIPIENTS
```

An **empty** `MAIL_ALLOWED_RECIPIENT_DOMAINS` allows the requester and nobody else. There is no
wildcard value — a deployment that wants wide sending lists its domains.

## 4. `email_sends` row

| Column | Note |
|---|---|
| `id` | uuid pk |
| `workspace_id` | fk, cascade |
| `flow_execution_id` | fk, nullable — null for a tool test call |
| `step_id` | text, nullable — from the step batch when present |
| `recipients` / `cc` | jsonb string arrays, post-resolution |
| `resolved_from` | `requester` \| `explicit` |
| `subject` | text — kept; it is the only human-readable handle on the message |
| `outcome` | `sent` \| `refused` \| `failed`, CHECK-constrained |
| `graph_message_id` | text, nullable — the correlation id |
| `failure_reason` | text, nullable |
| `created_at` | timestamptz default now |

**No body column, deliberately.** The body is the script's output, may contain tenant PII, and the
record exists to answer "was a message sent, to whom, and did it work" — which it does without it.
