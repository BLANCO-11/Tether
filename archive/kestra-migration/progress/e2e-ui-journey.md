**What this exercise can and cannot say.** It drives the same HTTP surface `packages/client` drives, so it can say *the client's calls behave as documented*. It is not a browser: it does not render a component, does not run the middleware session check with a real session, and does not open the progress WebSocket — it only proves the ticket that authorises one is minted. And a green journey is **not a correct automation**: the one step that can say correct is the oracle comparison, which is why it is in here.

## What to do about it

Ordered by how much a reader would be misled by the current state, not by how hard the fix is.

### MISMATCH — step 45: `— the api receiver's credential vs the token in its URL`

**Intended.** An `api` trigger is described as adding a credential on top of a webhook — two things a caller must hold, so that leaking the URL is not the same as leaking the ability to fire it.

**Real.** The Bearer value that succeeded is BYTE-IDENTICAL to the token in the URL — the credential seam resolves an api trigger's ref to its own `webhookToken`. The constant-time check is real and refuses a wrong value, but it is the same secret presented twice, and the client renders that secret as `webhookPath`. Say 'the token must be presented twice', never 'credential-authenticated' — and treat the URL as the credential when deciding who may see it.
